## RÈGLES SPÉCIFIQUES AU DASHBOARD PARTENAIRE

### Règle P-01 : KPI Cards Dashboard Partenaire
Le dashboard partenaire DOIT afficher les 4 KPI cards suivants :
1. **Total achat carburant par produit** (depuis début du mois) - Une card par type de carburant (SP95, SP91, GO, Pétrole)
2. **Total ventes par produit** (depuis début du mois) - Une card par type de carburant
3. **Total achat lubrifiants** (depuis début du mois) - Une card avec le volume total
4. **Doléances ouvertes** - Une card avec le nombre et code couleur (Orange si > 0, Vert si = 0)

**Période** : Du 1er du mois courant à aujourd'hui
**Unité** : Litres pour carburant et lubrifiants
**Source** : Tables `achats_carburant`, `shifts_carburant`, `achats_boutique`, `doleances`

---

### Règle P-02 : Niveau de Stock par Station avec Seuil Alerte
Le dashboard partenaire DOIT inclure un tableau affichant le niveau de stock actuel pour chaque station et chaque produit de carburant.

**Colonnes obligatoires** :
- Nom de la station
- Type de carburant (SP95, SP91, GO, Pétrole)
- Stock actuel (litres)
- Seuil d'alerte (litres)
- Capacité maximale (litres)
- % de remplissage
- Statut (OK / Alerte)

**Indicateur visuel** :
- Si stock_actuel ≤ seuil_alerte : ROUGE avec icône ⚠️
- Si stock_actuel > seuil_alerte : VERT avec icône ✓

**Source** : Table `cuves` + `stations`

---

### Règle P-03 : Réalisation vs Objectif Mensuel avec Projection
Le dashboard partenaire DOIT afficher pour chaque station la réalisation actuelle, l'objectif mensuel, le % de réalisation et une projection fin de mois.

**Calcul de la projection** :
- Jours écoulés = date actuelle - 1er du mois
- Jours restants = dernier jour du mois - date actuelle
- Vitesse journalière = réalisation actuelle / jours écoulés
- Projection = réalisation actuelle + (vitesse journalière × jours restants)

**Indicateur visuel** :
- % ≥ 100% : VERT
- 80-99% : ORANGE
- < 80% : ROUGE

**Source** : Table `objectifs` + `shifts_carburant`

---

### Règle P-04 : Réalisation vs Objectif Annuel avec Projection
Le dashboard partenaire DOIT afficher pour chaque station la réalisation annuelle, l'objectif annuel, le % de réalisation et une projection annuelle.

**Calcul de la projection annuelle** :
- Jours écoulés = date actuelle - 1er janvier
- Jours restants = 31 décembre - date actuelle
- Vitesse journalière = réalisation annuelle / jours écoulés
- Projection = réalisation annuelle + (vitesse journalière × jours restants)

**Indicateur visuel** : Même code couleur que mensuel

**Source** : Table `objectifs` + `shifts_carburant`

---

### Règle P-05 : Niveau Écarts Station
Le dashboard partenaire DOIT afficher le niveau des écarts de carburant pour chaque station avec tendance.

**Colonnes obligatoires** :
- Nom de la station
- Type de carburant
- Écart total du mois (litres)
- Nombre d'écarts
- Écart moyen (litres)
- Tendance (amélioration / dégradation)

**Calcul** :
- Écart total = SUM(ecart) WHERE date_inventaire >= 1er du mois
- Nombre d'écarts = COUNT(*) WHERE date_inventaire >= 1er du mois
- Écart moyen = Écart total / Nombre d'écarts

**Indicateur visuel** :
- Écart positif : VERT
- Écart négatif < 5% : ORANGE
- Écart négatif ≥ 5% : ROUGE

**Source** : Table `inventaires_carburant`

---

### Règle P-06 : Statistiques Doléances Avancées
Le dashboard partenaire DOIT afficher des statistiques détaillées sur les doléances incluant délai moyen par TM et délai global.

**Section 1 : Vue globale réseau**
- Nombre total de doléances ce mois
- Délai moyen de traitement réseau
- Délai moyen d'accusé de réception
- Délai moyen de résolution

**Section 2 : Vue par Territory Manager**
- Pour chaque TM : nombre de doléances assignées, délai moyen accusé réception, délai moyen résolution, % résolues

**Calcul des délais** :
- Délai accusé réception = date_prise_en_charge - date_envoi
- Délai résolution = date_cloture - date_prise_en_charge
- Délai total = date_cloture - date_envoi

**Unité** : Heures ou jours (configurable)

**Source** : Table `doleances` + `users` + `stations`

---

### Règle P-07 : Filtre par Territory Manager
Le dashboard partenaire DOIT permettre de filtrer toutes les données par Territory Manager (vue sur la zone géographique).

**Filtre global** :
- Sélecteur en haut du dashboard
- Options : "Tout le réseau" (par défaut) + liste des TM du partenaire
- Impact : Tous les KPIs et tableaux sont recalculés pour la zone du TM sélectionné

**Impact du filtre** :
- KPI cards : Données des stations de la zone du TM
- Tableau stocks : Stations de la zone du TM
- Tableau réalisations : Stations de la zone du TM
- Tableau écarts : Stations de la zone du TM
- Stats doléances : Doléances de la zone du TM

**Source** : Table `users` (TM) + `stations` (zone_geographique ou tm_id)

---

### Règle P-08 : Date de Dernière Mise à Jour par Station
Toutes les données affichées dans le dashboard et les rapports partenaire DOIVENT indiquer la date de la dernière mise à jour pour chaque station.

**Affichage** :
- Dans chaque tableau : colonne "Dernière mise à jour"
- Dans chaque KPI card : mention "Mis à jour le : JJ/MM/AAAA"

**Dates par type de données** :
- Stocks : Date du dernier inventaire validé
- Ventes : Date du dernier shift clôturé
- Achats : Date de la dernière réception
- Écarts : Date du dernier inventaire avec écart
- Doléances : Date de la dernière doléance
- Réalisations : Date du dernier shift clôturé

**Format** : JJ/MM/AAAA HH:MM

**Source** : Tables `inventaires_carburant`, `shifts_carburant`, `achats_carburant`, `doleances`

---

### Règle P-09 : CA Boutique dans les Rapports Uniquement
Le chiffre d'affaires (CA) boutique NE DOIT PAS apparaître dans le dashboard partenaire, mais DOIT être disponible dans les rapports détaillés.

**Dashboard** :
- NE PAS afficher le CA boutique dans les KPI cards
- NE PAS afficher le CA boutique dans les graphiques

**Rapports** :
- Ajouter un rapport spécifique "CA Boutique par Station"
- Ce rapport DOIT afficher : CA boutique total par station, par famille, par article, évolution, réalisation vs objectif

**Raison** : Le dashboard reste une vue générale synthétique, le CA boutique est un détail consultable dans les rapports.

---

### Règle P-10 : Rapports Détaillés par Station
Les rapports partenaire DOIVENT permettre de voir les détails par station. Le dashboard reste une vue générale, mais les rapports doivent contenir les détails complets.

**Rapports concernés** :
- Rapport volumes vendus par station
- Rapport stocks par station
- Rapport écarts par station
- Rapport réalisations vs objectifs par station
- Rapport doléances par station

**Fonctionnalité** :
- Chaque rapport DOIT avoir un filtre par station
- Possibilité de sélectionner une ou plusieurs stations
- Possibilité d'exporter le rapport pour une station spécifique

## RÈGLES MÉTIER QUI RESTENT INCHANGÉES (Guide_Document_SuccessFuel.md)

### Règle G-01 : Partenaire - Données Opérationnelles Uniquement
Le partenaire NE DOIT JAMAIS voir :
- CA carburant
- Marges
- Données financières
- Données comptables
- Trésorerie détaillée
- Salaires
- Charges

Le partenaire DOIT voir :
- Volumes vendus (carburant)
- Stocks
- Achats
- Réalisations vs objectifs
- Écarts stocks carburant
- CA boutique (sans marges)

---

### Règle G-02 : Sessions Employés - Droits Granulaires
Les sessions employés DOIVENT avoir des droits granulaires par poste (page par page, fonctionnalité par fonctionnalité), JAMAIS par rôle hiérarchique.

**Côté partenaire** :
- Admin partenaire voit tout le réseau
- Territory Manager est filtré par zone géographique

---

### Règle G-03 : RLS Strict
RLS strict sur toutes les tables sensibles :
- Chaque gérant ne voit que les données de ses entreprises/stations
- Le partenaire voit uniquement les données opérationnelles des stations de son réseau (jamais financières)
- Les sessions employés héritent des droits du compte parent + restrictions supplémentaires

---

### Règle G-04 : Partie Double Bloquante
Partie double obligatoire et bloquante : ∑ Débits = ∑ Crédits, sinon BLOQUÉ.

---

### Règle G-05 : CMUP Seule Méthode
CMUP est la seule méthode de valorisation, calculé via `calculer_cmup()` (trigger SQL).

---

### Règle G-06 : Numéros de Comptes Invisibles
Numéros de comptes sont INVISIBLES en frontend partout sauf Grand Livre et Balance (option).

## RÈGLES TECHNIQUES (CLAUDE.md)

### Règle T-01 : Stack Technique
- Next.js 16 (App Router)
- TypeScript strict
- Tailwind CSS
- shadcn/ui UNIQUEMENT
- Supabase UNIQUEMENT
- TanStack Query
- Zustand (authStore, uiStore)
- next-intl (fr/en)
- PWA (Service Worker offline)
- Zod validation
- Vitest + Playwright
- recharts
- Vercel

---

### Règle T-02 : Architecture Projet
- `/app/(auth)/` — login, signup, first-login, callback
- `/app/(onboarding)/` — multi-step setup wizard
- `/app/(manager)/manager/` — gerant dashboard
- `/app/(admin)/admin/` — superadmin
- `/app/(partner)/partner/` — partenaire
- `/components/` — composants partagés
- `/services/` — services Supabase
- `/hooks/` — hooks custom
- `/lib/` — utilitaires
- `/types/` — types TypeScript

---

### Règle T-03 : Supabase Clients
- `src/utils/supabase/client.ts` — browser client
- `src/utils/supabase/server.ts` — async server client with cookies
- `src/utils/supabase/admin.ts` — service-role client (server-only)

NEVER MIX ces clients.

---

### Règle T-04 : State Management
- **Zustand** : `authStore` (user, compte, entreprise, role helpers) et `uiStore` (sidebar, locale, theme)
- **React Query** : all server data (list queries, mutations)

---

### Règle T-05 : Service Layer
All Supabase queries live in `src/services/`. Components call service functions, not Supabase directly.

---

### Règle T-06 : Forms
React Hook Form + Zod. Schemas are colocated with their form components or in `src/lib/`.

---

### Règle T-07 : i18n
`next-intl` with locales `fr` (default) and `en`. UI is predominantly French.

---

### Règle T-08 : Design System
Palette Dark Mode (--or, --blu, --nav, --grn, --bg, --card, --red, --gold). Mobile-first, responsive.

---

### Règle T-09 : Testing
- Unit tests: `src/lib/__tests__/` and colocated `*.test.ts` files
- E2E tests: `e2e/` directory
- Linting ESLint 0 erreur
- TypeScript tsc --noEmit 0 erreur
- Build npm run build réussit
